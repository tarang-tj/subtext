# Testing protocol

Subtext has not yet been tested with an autistic teenager. This is the session that would fix that, written in advance so it can be run by someone who was not involved in the build.

It is designed to be worth running in fifteen minutes, because that is realistically what a first session gets.

## Before the session

- Camera off by default. Say so unprompted rather than waiting to be asked.
- Written questions sent in advance, so nothing depends on processing speech in real time.
- Say at the start that there are no wrong answers and that the tool is what is being tested, not the person. Then do not repeat it, because repeating it is its own kind of condescension.
- Offer text chat as an equal option to voice. Not as a fallback for people who "can't" do voice.
- Agree a stop word. Use it without discussion if it is said.

## What we are actually trying to find out

The build rests on four assumptions. Each one could be wrong, and the session is worth running only insofar as it can disconfirm them.

| # | Assumption | What would disconfirm it |
|---|---|---|
| A1 | Showing a spread of readings with confidence numbers is more useful than one confident answer | The tester finds the spread paralysing, or wants to be told the answer |
| A2 | The suggested clarifying question is something they would actually send | They say it sounds unnatural, blunt in the wrong way, or like something an adult wrote |
| A3 | The refusal to soften reads as respect rather than as the tool being unhelpful | They wanted the softer version and are annoyed it was withheld |
| A4 | The "where this comes from" panel is reassuring rather than clinical or patronising | They ignore it, or it reads as the tool justifying itself at them |

A4 is the one most likely to be wrong.

## The session

**1. Decode, with their own material (5 min).**
Ask them to paste a real message they were unsure about, if they are willing. If not, use the "can we talk later" example. Watch where they look first and what they skip. Do not narrate.

Ask afterwards, in this order:
- What did you look at first?
- Was anything on that screen useless to you?
- Would you have sent that question at the bottom? If not, what is wrong with it?

**2. Forecast, and the refusal (5 min).**
Have them write something direct they have actually needed to send. Let them hit the masking block if it fires; if it does not fire naturally, show them the blocked example.

- When it said it would not make that softer, what did you think?
- Is that the right call, or would you have wanted the softer version?

**3. The honesty panel (3 min).**
Open "where this comes from".
- Does this change anything about whether you would trust it?
- Does it feel like it is explaining itself to you, or at you?

**4. Close (2 min).**
- What would you delete from this?
- What would make it not worth using?

Ask what they would delete rather than what they would add. Everyone can name a missing feature; only a real user can tell you what is dead weight.

## After

- Write down what was said before interpreting it, and keep the two separate in the notes.
- Any finding that contradicts a design decision gets recorded even where there is no time to act on it. The record is what makes the next version accountable to this one.
- If a claim in the README is contradicted by what a tester says, the README changes. The tester is the better source.

## What this protocol cannot do

One session with one person is not evidence about autistic teenagers in general, and the write-up should not be phrased as though it were. It is one person's account of one tool, which is considerably more than this project currently has, and considerably less than it needs.
